# Release site

Builds a GitHub Pages site from `content/index.md` plus the releases of two
upstream (public, read-only) repos. Each release shows a short "What's new" list, written by people
(optionally drafted with an AI assistant and reviewed) and committed in
`content/summaries/`, with the original notes in a collapsed block.

## How it works

- `.github/workflows/pages.yml` runs on push to `main`, every 6 hours, and on demand.
- `scripts/build.py`:
  1. Fetches all releases (prereleases included) of each repo in `site.config.json`.
  2. Caches each **new** release once in the `release-cache` branch
     (`<owner>__<repo>/<release_id>.json`). Cached releases are never re-rendered;
     releases deleted upstream are removed.
  3. Takes each release's "What's new" list from
     `content/summaries/<owner>__<repo>/<tag>.md`. Releases without one show
     "Summary not available yet" and their original notes. See
     `content/summaries/README.md` for the format and writing guidelines.
  4. Renders `index.md` (via GitHub's markdown API), inserts the release cards
     at `{{releases:owner/repo}}` markers, wraps it in `templates/page.html`,
     copies `static/` and writes `_site/`.
  5. Builds `upcoming.html` from `content/upcoming.md`. Its `{{roadmap}}` marker
     is replaced by planned-release cards fetched from the roadmap repo set in
     `site.config.json` → `roadmap` (`"path"` is the folder holding one markdown
     file per planned version, e.g. `"releases"`). Each file becomes one card,
     labelled with its platforms, with optional "Android only" / "iPhone only"
     lists. See `../release-roadmap/README.md` for the format. A snapshot of the roadmap
     is kept in the cache, so upstream roadmap edits trigger a deploy on the next
     scheduled run, and a failed fetch falls back to the last good copy.
     Both pages share a nav bar.
- Scheduled runs only deploy when something changed. Pushes always deploy,
  so editing `upcoming.md` on GitHub publishes it straight away.

## Setup

1. Put the real repos and descriptions in `site.config.json`, and the same
   repo names in the markers in `content/index.md`.
2. Write your page in `content/index.md` and your CSS in `static/style.css`.
3. Push to the `main` branch of a GitHub repo.
4. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
5. Run the workflow once from the **Actions** tab (or push). The first run
   creates the `release-cache` branch and starts the backfill.

No secrets are needed: the workflow's own `GITHUB_TOKEN` is used for the GitHub API.

## Day to day

| Task | How |
|---|---|
| Merged vs per-platform lists | In `content/index.md`, `{{releases:merged}}` shows one card per version across all repos (paired by version number, `v` prefix ignored, labelled with each repo's `platform`). `{{releases:owner/repo}}` shows one repo's list. |
| Update planned releases | Edit the roadmap repo; the site picks it up on the next scheduled run (or run the workflow manually) |
| See which releases need a summary | `python3 scripts/build.py --list-missing` (prints the file path to create for each; add `--limit N` for the newest N) |
| Draft missing summaries | `scripts/draft-summaries.sh [N]`, then review and commit (see [Writing summaries](#writing-summaries)) |
| Add or fix a summary | Edit `content/summaries/<owner>__<repo>/<tag>.md` and push; it's live on the next build |
| Change schedule | `cron` in the workflow |

Edits to existing upstream release notes are intentionally ignored. To pick
one up, delete its file from the `release-cache` branch.

## Writing summaries

Summaries are never generated by the workflow. They're plain files in
`content/summaries/`, written by a person or drafted locally with Claude Code
and reviewed before they're committed. The format and writing guidelines are in
[`content/summaries/README.md`](content/summaries/README.md).

### Backfilling (or catching up after new releases)

Needs `python3`, the [`claude` CLI](https://claude.com/claude-code) (logged in),
and a clone of this repo.

1. See what's missing:

   ```sh
   python3 scripts/build.py --list-missing
   ```

2. Draft summaries for the newest unsummarised releases, in batches (20 by default):

   ```sh
   export GITHUB_TOKEN=<token>      # optional; avoids GitHub's low anonymous rate limit
   scripts/draft-summaries.sh 20
   ```

   The script fetches the releases, exports the notes of those without a
   summary to a temporary folder, and runs Claude Code non-interactively to
   write one summary file per release. Claude can only read those notes and
   the writing guide, and only write files: no shell commands, no web access,
   no commits. Set `CLAUDE_MODEL` (e.g. `CLAUDE_MODEL=sonnet`) to choose the model.

3. Review the drafts. Changes too vague to summarise without guessing are kept
   in the files as `# Unclear:` comments, holding the original line from the
   release notes (with its PR link). They're never shown on the site:

   ```sh
   git status content/summaries
   grep -rn --exclude=README.md "^# Unclear:" content/summaries   # vague items to look up and resolve
   ```

   To resolve an unclear item, replace the comment with a proper item, or
   delete it if the change doesn't matter to users. You can commit with
   unclear items still in place and come back to them later.

   Edit or delete any file you're not happy with. A release without a file
   just shows its original notes.

4. Commit and push. The site rebuilds and publishes the summaries straight away.

5. Repeat steps 2–4 until `--list-missing` reports every release has a summary.

To draft by hand instead, copy the paths from `--list-missing`, read each
release's notes on GitHub, and write the files yourself. You can also ask Claude
Code interactively (see the end of `content/summaries/README.md`).

### After new releases

New releases appear on the site straight away, showing "Summary not available
yet" and their original notes. Run `scripts/draft-summaries.sh` again to draft
summaries for them, review them and push.

```sh
GITHUB_TOKEN=<token> python3 scripts/build.py   # writes ./cache and ./_site
```
